# 工場記録の再送・発生版・解消根拠

2026-09-13。工場記録の修理に関する親の採用判定。公開後の受入結果はcampaign計画で追跡する。

## 確認した原因と採用する変更

- 累積記録の同じ件数・発生時刻が、導入版の更新後に再送されると再発に見えた。受信側は実発生の前進を判定し、再送で既知の発生版を上書きしない。同版の新規発生は再発として扱う。
- 製品の公開snapshotで発生版が落ち、Aitermとsidecarでは同じ集約への再発でも初回版が残った。製品が発生版を所有し、工場は公開値を投影する。復元不能な旧集約は版不明として移行する。
- runtimeや診断が新版の報告から消えただけでは修理成功を証明できない。runtimeは製品の明示解消、診断は対象checkの成功を根拠とする。構造的な非対応・対象外は別の理由として保持する。
- 既存の誤再発の訂正では、製品の解消通知を一次観測と照合し、その後の全観測で当該記録が欠けず、件数・発生時刻・初回発生時刻が基準と同じことを確認する。新規発生、欠損、解消通知のない記録は隠さない。
- 定期報告のwire不一致とcronの最小PATHでのnode不在を再現した。正規schedulerを設定から更新し、Linuxの正規入口で公開CLIのPATHを整える。製品更新周期は変更しない。

## 反証への判定

Grokの実ファイル反証で指摘された、再評価による発生版上書き、解消通知の未照合、native_diagnostics欠落の自動解消を採用して修理した。再送時の別版・版欠落と、一次解消通知欠落のfixtureで確認した。

解消通知より前の欠損だけでは、解消後の新しい発生は証明できないため、一律の解消禁止条件にはしない。解消後の欠損や件数・時刻の変化は訂正を拒否する。集約世代が件数・初回時刻・最終時刻のすべてを保持したまま別エラーへ切り替わるという反例は実測されていないため、推測によるschema番号制限は追加しない。

Chat Proには基準commitのGitHub URL、現在の実コード、再現条件、具体的な問いを渡した。Aiterm移行の添付相談ではPro選択、添付の読戻し、回答完了をMCP結果で確認した。添付のMIME確定とPro待機時間に実在したconnector欠陥も製品repoで修理した。失敗した相談を成功の根拠には含めない。

## 検証と本番の境界

受信・移行・再送・同版再発・発生版表示のfocused testを通し、ServerManagerの必須npm testを実行した。WebUIの隔離fixtureで、最新版の優先、過去版と版不明の明示、解決済みの既定非表示、最新版だけへの絞込みを確認した。

本番はconsumer、工場reporter、producerの順に互換性を整える。正式配備のDB backup・revision照合・readinessを通し、履歴修復は正式CLIのdry-runと入力digestを用いる。直接SQLで本番記録を補正しない。
