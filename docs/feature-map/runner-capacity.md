# Factory runner capacity: load-driven runner pool per host

[Overall index](../09_feature-map.md) / [factory-ci runbook](../../shared/runbooks/factory-ci.md) / [contract](../../lib/factory/deployment-contract.mjs) / [current state](../factory-current-state.md) / [setup](setup.md) / [CI](ci-distribution.md)

Why: on 2026-11-08 the Owner directed parallel CI on existing factory hardware, then (11:1x JST) "decide the parallelism dynamically from real load, Mac too, minimum 1; CPUs dynamic too". The fixed design of the same morning (Rabbit 2 / Fox 3 instances, one pinned CPU set each, CPUs 0-7 reserved) is replaced: each seat keeps a POOL of registered runner instances under the SAME host label and the SAME dedicated non-admin principal, and ONE scaler per host decides from measured CPU idle, run-queue load (where the seat sets a limit) and available memory how many listeners run (1 to pool size). No CPU affinity except the Fox per-job CPU budget (2026-11-14, below); elsewhere every job sees all CPUs (`os.availableParallelism()`); every job runs at low priority, so the Owner's interactive work wins and also lowers the measured idle, which stops further scale-up.

Mac load gate (2026-11-08 18:0x JST, Shiratsuru/Snow): the first natural Mac pair (17:34-17:54 JST) failed two Lattice latency tests (1000 ms daemon identity probe, 5000 ms beforeEach) while the Mac's 1-minute load average was 50-520 on 10 CPUs (Nextcloud FileProvider, fileproviderd, Spotlight, media analysis, ESET). The scaler had started u3 at CPU idle 0.349 because background-QoS daemons queue on the efficiency cores while the performance cores show idle; idle alone does not show the queue. A second/third Mac job therefore also needs the 1-minute load average per logical CPU <= 1.0 (no run queue on average). Sample 17:59 JST with one job: load 50-60, idle 0.06-0.10 → hold. Linux/Windows keep idle + memory only.

Mac concurrency cap (2026-11-13 JST, Shiratsuru decision from Xuan's analysis and Dorothy's host readback): rule **max 1 concurrent `macos-native` runner on MacBook-Air; reason CPU contention 2026-11-13; reopen if Mac queue wait becomes the bottleneck.** Lattice full runs on u2 + u3 (15:19-15:42Z 11-12) failed together on fixed timing windows: CPU idle 0.505 → 0.01, load per CPU ~2.1 on 10 CPUs; no fd limit was near (`kern.num_files` 5.4 % of `kern.maxfiles`, ≤ 41 fds per node process). Over 63 Mac full jobs 11-08..11-12 overlapped jobs failed 29 % vs 15 % solo. The load gate samples only at start (u3 started at load per CPU 0.54 while one suite ran), so it cannot prevent the overlap; the scaler cannot know which job a listener will receive. Contract `maxRunning: 1`; u2/u3 stay registered and are refreshed by rotation. Rollback: drop `maxRunning` (pool 3).

Fox per-job CPU budget (2026-11-14 JST, Owner ruling): rule **each `windows-native` job runs on one 8-CPU block of Fox's 32 logical CPUs, at most 4 jobs at once (32 / 8); reason CPU oversubscription 2026-11-14.** At 05:18-05:43Z 3-4 full Windows suites from different repos ran at once (aiterm-mcp on u6, Throughline on u, Lattice on u7 and u2). With no CPU limit each suite sized itself to the whole host (`node --test` default `availableParallelism() - 1`; the job log shows `FACTORY_CI_JOBS=32`), so concurrent suites added contention, not throughput; Aiterm had 5 Windows-only timing failures (Elegg's read-only evidence), while runs with no other Fox job passed. Shiratsuru's first decision (max 1 concurrent, PR #41, not merged) was replaced by the Owner the same day: the promise is parallel CI, and one job using all 32 CPUs is the irregularity. Mechanism: the job-started hook sets the Runner.Worker's processor affinity (inherited by every step) to the block that overlaps the fewest other Runner.Workers, under a named mutex so simultaneous starts pick different blocks. Block choice on ties (2026-11-14 JST, Shiratsuru decision from Elegg's evidence, elegg-aiterm/w2): **least-loaded block by one per-CPU sample at job start; sample failure: highest index; reason Owner desktop load on the low CPUs 2026-11-14.** With lowest-index ties a lone job always got block 0 (0xFF) while CPUs 0-3 were 78-94 % busy from the Owner's Normal-priority desktop work (nikke, ESET, SearchIndexer, dwm) and CPUs 8-15 sat near 1 %; the BelowNormal job got little CPU (Aiterm full suite 802 s vs 484 s, 8 PTY timing failures, job 132377918670). Fewest overlap still decides first, so concurrent jobs keep separate blocks. Probe on Fox (Node v24.22.1): a process started under an 8-CPU affinity reports `availableParallelism()` 8 (`os.cpus().length` stays 32), so `FACTORY_CI_JOBS` and `node --test` follow the block. Contract `cpusPerJob: 8` (hook default) and `maxRunning: 4`. No Owner-reserved CPUs: BelowNormal priority keeps the Owner's work first. Rollback: previous hook (no affinity) and config (no `maxRunning`), task restart while idle.

Fox memory reserve (2026-11-08 18:5x JST, Shiratsuru decision): Lattice windows jobs failed on 5000/1000 ms timeouts 08:57-09:43Z, the first one alone on fox-u. CPU was not the limit (29-45 % busy, queue 0-3, idle 0.763 at the only scale-up), memory was: available 2.2-5.7 GB of 61.6, hard page reads up to 4.3k/s, disk time up to 214 % while the Owner's ComfyUI held ~45 GB private. The scaler had started u2 at 7.24 GiB (3 + 4). reserveGiB 4 → 12, so a 2nd Fox job needs >= 15 GiB available.

Mac work folder: Spotlight indexed the runner roots, `_work` and `RUNNER_TEMP` (`_work/_temp`) (root `mdfind -name` hits, 18:0x JST). `.metadata_never_index` is not honored for folders on macOS 27 (probe: still indexed); a folder named `*.noindex` is excluded with all descendants (probe: control 1 hit, `.noindex` 0, nested 0). The Mac roots therefore use work folder `_work.noindex` (`.runner` `workFolder`; new registrations `--work _work.noindex`), which also moves `RUNNER_TEMP` and the tool cache. `.path` (2026-11-08 18:4x JST): `config.sh` rewrites `.path` from its own environment, and the apply scripts run it with a minimal PATH, so Mac u2/u3 lost `/opt/homebrew/bin` (dotagents CI on u3: `node: command not found`; Lattice uses the factory node and passed) and Rabbit u2..u5 lost `/usr/local/bin` (ollama only). The scaler starts each listener with its root's `.path`, so the apply scripts copy the first root's `.path` to every pool root after registration. The roots' static `bin`/`externals` stay indexed (written only on runner update); moving the roots would need re-registration.

## Rootless Docker for Rabbit jobs (2026-11-22)

Why: License-DB run 44951824444 (`docker-check`: buildx `test` target for amd64 and arm64 via qemu, then a GHCR publish) and OLTranslator run 44953408774 job 136996124277 (`docker build -f server/Dockerfile server` on `factory-linux-rabbit-u5`) failed with `permission denied` on `/var/run/docker.sock`; npm ci and the tests passed. Rule (Shiratsuru decision, task `ci-rabbit-docker/d1`): **`factory-runner` never joins the `docker` group; its jobs use a rootless Docker daemon owned by `factory-runner`.** The group would be host root for every job, and runner group 1 also serves public repos; the principal is deliberately group-less (`ensure_github_actions_runner` refuses extra groups), runs the runner/scaler unit with `NoNewPrivileges` and no capabilities, and that stays.

- Daemon: `factory-runner-dockerd.service` (own unit, `User=factory-runner`, `ExecStart=/usr/bin/dockerd-rootless.sh --host unix:///run/factory-runner-docker/docker.sock`). `newuidmap`/`newgidmap` are setuid, so this unit cannot set `NoNewPrivileges`; that is why it is a separate unit and the runner/scaler unit is unchanged. `RuntimeDirectory=factory-runner-docker` (0700, owned by `factory-runner`) holds the socket, so no other user reaches it. `Nice=10` and `CPUWeight=20` as the scaler unit: build work runs in this cgroup, not the scaler's, and must also yield to the Owner. Image and container data live under `/home/factory-runner/.local/share/docker` (same disk as the pool roots; growth is unmanaged, see "Unconfirmed").
- Packages (only what is missing): `uidmap`, `slirp4netns`, `qemu-user-static`, `docker-ce-rootless-extras` pinned to the installed `docker-ce` version (exists only in Docker's apt repository; with another Engine origin the apply stops before any change). `factory-runner` gets a 65536-id `/etc/subuid` and `/etc/subgid` range after the existing ones if it has none. Ubuntu 24.04+ with `kernel.apparmor_restrict_unprivileged_userns=1` also gets the AppArmor profile Docker documents for `/usr/bin/rootlesskit` (`userns,`), written only if absent and marked for rollback.
- Jobs: every pool root's `.env` gets exactly one `DOCKER_HOST=unix:///run/factory-runner-docker/docker.sock`. The Listener reads `.env` as `KEY=VALUE` lines when it starts (actions/runner `Program.LoadAndSetEnv`) and jobs inherit it, so it works with the scaler starting `Runner.Listener` directly. Already running listeners keep the old environment until they restart, so the apply stops idle listeners; the scaler starts them again (minimum 1, then on load).
- arm64: the host registers `qemu-aarch64` binfmt with the F (fix-binary) flag; the kernel opens the interpreter at registration, so containers inside the rootless user namespace run arm64 binaries without a qemu copy and without `docker/setup-qemu-action` (`--privileged`). The packaged flags are kept; F is added in `/etc/binfmt.d/qemu-aarch64.conf` only when missing.
- Other products are unaffected: no group, no `/var/run/docker.sock` change, the rootful `docker.service` keeps serving the Owner's user. Workflow changes in License-DB and OLTranslator are their owners'.

Runner umask and host packages (2026-11-22 JST, Shiratsuru request from Mihara's grok-build-desktop-kitepon PR#13, run 44969879517): (1) **Mac jobs run under umask 022 (LaunchDaemon `Umask` 18), as GitHub-hosted runners do.** The plist had `Umask` 63 (077) since the scaler swap; dotagents records no reason for it (no doc, ADR or commit message explains 077; the plist took over the old per-runner daemon's settings), so it is changed. Symptom: `test/codex-managed-installer` was created with mode 0700 instead of 0755. The pool roots stay private because the apply creates them under an explicit `umask 077`, and files the runner writes with explicit modes (credentials) are unaffected. A process keeps the umask it started with and adopted listeners outlive the scaler, so the apply also stops idle listeners (never with a Worker running); the scaler starts them again under 022. (2) **Rabbit gets host packages for GUI integration tests and Linux app packaging**: `xvfb xauth xdotool squashfs-tools desktop-file-utils apparmor` and `libfuse2t64` (`libfuse2` below Ubuntu 24.04), added by the Linux root phase for the `linux` variant only (never `server`). The runner principal is unchanged (no groups, NoNewPrivileges, no capabilities), which is why jobs cannot apt-get them. (3) Mac Homebrew locks: the runner principal is a non-admin user and `/opt/homebrew` belongs to the admin owner, so `brew install` from a job fails on `/opt/homebrew/var/homebrew/locks` by design. Jobs may use what is installed (`/opt/homebrew/bin` is on the PATH) but never install host packages; a tool a product needs is added by a host apply, named per product.

## State diagram (one pool instance, as seen by the scaler)

| From | Event / condition | To | Note |
| --- | --- | --- | --- |
| unregistered | host apply registers the root | stopped | Only the admin step registers. |
| stopped | `running < desired`, least-recent `lastRun` first | idle | start |
| stopped | headroom AND `running < cap` AND `lastRun` older than 7 days | idle | refresh: GitHub deletes self-hosted runners offline > 14 days; trimmed again after 120 s idle. New roots (no `_diag`) refresh first. |
| idle | `running >= cap` AND a stopped root's `lastRun` older than 7 days AND idle >= 120 s | stopped | refresh-rotate: frees the slot; the next tick's start picks the stale root (least-recent `lastRun`), so the cap is never exceeded. |
| idle | Runner.Worker appears | busy | |
| busy | Worker exits (job end) | idle | self-exit of the "never stop busy" guard |
| idle | `running > desired` AND idle >= 120 s, longest idle first | stopped | SIGINT / Ctrl+Break: graceful, deletes the session |
| idle / busy | listener exits by itself (self-update, error, session conflict) | stopped | next tick re-decides |

`busy` = roots with a Runner.Worker. `headroom` = CPU idle >= 30 % (60 s window complete) AND (no `maxLoadPerCpu`, or 1-minute load average / logical CPUs <= `maxLoadPerCpu`) AND available memory >= `jobGiB + reserveGiB`. `cap = min(registered, maxRunning ?? registered)`; `desired = clamp(busy + (headroom ? 1 : 0), 1, cap)`; busy >= cap fails headroom with gate `max` (logged as a hold). One action per tick. Guards (named protection): a busy listener is never stopped (running job = data loss); the count never goes below 1 (Owner minimum); the cap only withholds a start (protects the running jobs' CPU, the 2026-11-13 Mac and 2026-11-14 Fox failures) and frees by itself when the job ends. All leave by themselves: the job ends, or more load arrives.

Available memory: Linux `os.freemem()` (MemAvailable), Windows `os.freemem()` (available physical), macOS `kern.memorystatus_level` (the system's memory-free percentage, as `memory_pressure` prints) × physical memory; `vm_stat` free + inactive pages miss compressible memory (2026-11-08 14:1x JST, one Lattice job running: 5 GiB by pages vs 42 % = 10 GiB free, 5 GiB swap in use).

## Deployment, admission and rollback

Order per host: (1) register the new pool roots while the existing listeners keep working; (2) install scaler + config; (3) swap the supervisor (old units/plist/task children) only when no Runner.Worker exists.
