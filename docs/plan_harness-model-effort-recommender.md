# ハーネス・モデル・エフォート推薦ツールの実装計画

作成日: 2026-09-21。状態: **計画を記録。実装未着手**。次の着手点は工程1のCursor・Grok残量取得の実測。

## 目的と合意

親AIが任務と制約を一度渡すと、**ハーネス × モデル × エフォート**と短い選定理由を受け取れるツールを作る。任務への適性、実際に呼べる組合せ、契約プールの余裕を合わせて判断し、自然文の判断にはJevを使う。親が推薦のたびに[02_models.md](02_models.md)全文を読む負担を減らす。

本計画は2026-09-21のオーナー発言を次のように受け取る。

| 合意 | 実装への反映 |
|---|---|
| 提案対象はハーネス・モデル・エフォートの3点 | モデル名だけを返す設計にしない。effortの対応状況も候補の一部とする |
| 02は大事 | 任務・役割への適性とmodel×effortの判断正本を02に維持する |
| Claudeの契約は20ドルのProへ縮小 | 契約情報として保持し、残量の実測と区別する |
| Grokの枠は少なく、Cursorは余ることが多い | 必要な能力を満たす候補では、余裕のある契約プールを優先する |
| Claude系・Grok系モデルはCursorからも呼べる | 同じモデルでもハーネスが異なる候補を比較する。個々のmodel ID・effort・機能の対応は実環境で確認する |
| Claude系・Grok系はCursor経由を優先したい | Cursorで任務を満たせて枠が使える場合の運用優先順位にする。直接契約を使う推薦には理由を付ける |
| Jevを活用する | 能力・候補・残量をこちらから渡して選択させる。Jevがモデル性能や契約残量を内蔵している前提を置かない |

上記の契約情報は計画時点の申告であり、今後の現行値は所有する設定から読む。残量率だけで契約規模の違うプールを比較しない。CursorでClaude系を使う場合もGrok系を使う場合も、実際の課金・制限単位に従って同じプールへ関連付ける。モデル提供元と消費する契約を分ける。

## 設計方針

### 正本と責務

- **02**は役割・任務への適性、model×effortの選び方と根拠を所有する。機械可読な記述を02内に持たせ、推薦用の小さな候補データを生成する。同じ順位・判断を別の手書き設定へ複製しない。
- **ハーネスの公開情報と実測**から、利用可能なmodel ID、effort、context、道具・検索・実行機能を得る。モデルが同じでも、直接ハーネスの機能がCursorで同じように使えるとは仮定しない。
- **dotagentsの契約設定**はアカウントの識別子、共有プールの対応、オーナーの利用優先順位を所有する。認証情報と残量の観測値はここへ混ぜない。
- **残量取得部品**は取得元、取得時刻、制限窓、使用量・残量、単位、リセット時刻、取得状態を返す。数値がない場合は不明と返す。履歴用の観測時刻とキャッシュの有効期限を区別する。
- **コード**は利用可否・明示制約の判定、共有プールの同定、残量計算を担う。**Jev**は任務と候補の適合、必要なeffortの判断を担い、実在する候補IDから選ぶ。
- 推薦の実装と工場への接続はdotagentsが所有する。製品固有の認証・状態・PTY制御は所有製品の公開入口を利用し、不足があれば所有repoで修理する。残量取得のためにAitermの変更が必要かは工程1の証拠で決める。

### 一度の呼出しで完結する入口

最初の公開入口はdotagentsのCLIとし、内部実装を各親から同じ形で利用する。常駐サービスや新規MCPサーバーは最初の実装に含めない。コマンド名と配布位置は既存入口との衝突を確認して工程2で確定する。

入力は任務、既知なら役割、必要な機能、明示されたharness/model/effort、独立した反証に必要な元モデル提供元など、呼出し側の意図を表す情報だけとする。親に残量の手取得、複数コマンドの実行順、ハーネス固有のオプション方言を要求しない。

入口は必要な残量・catalogを取得または有効な観測から読み出し、候補を絞り、Jevへ一括で判断を依頼して、次を返す。

| 出力 | 内容 |
|---|---|
| 推薦 | harness、model、effortの指定値と指定可否、消費するpool ID |
| 理由 | 適性・契約優先・残量の根拠。Jevが選んだ基準IDと観測値からコードで短く組み立てる |
| 観測 | 取得元、観測時刻、残量と単位、reset、不明・未対応・取得失敗の区別 |
| 状態 | 推薦成立、必要情報不足、適合候補なし、外部サービス失敗を識別できる結果 |

effortはハーネス×モデルの対応値から選ぶ。同じ`high`でも別モデル・別ハーネスで同等の計算量や性能とはみなさない。effortを指定できない候補は「指定不可」を返し、APIの`none`という有効な指定値や取得不能と区別する。明示指定が非対応なら、勝手に省略・変換せず理由を返す。

Jevは自由文の説明生成器として使わない。選択結果と、必要なら型付きの判断項目を受け取る。02全文を毎回Jevへ転送する設計にもせず、対象役割の判断基準と適合候補、必要な観測に絞る。

取得不能やJev失敗を隠して固定モデルを返すことはしない。他候補を推薦できる場合も、除外理由と欠けた観測を結果へ出す。残量比較の根拠が足りない場合は、その比較が成立したとは報告しない。

## 実装の順序と完了条件

工程1から順に進める。工程1で判明した公開入口・制限単位を工程2の契約へ反映し、その契約に従って工程3・4を実装する。技術的な工程完了を毎回のオーナー承認待ちにはしない。人のログイン操作や外部サービス対応が必要になった場合は、止まった位置と必要な操作を明示する。

### 工程1 — Cursor・Grokの残量を実際に取得する

1. Caveat・既存RAGを確認し、CursorとGrokの公式仕様、実環境の公開CLI・API・利用状況画面を調べる。アプリ契約の枠とAPI課金を混同しない。
2. Cursor・Grokそれぞれで、現在の契約の使用量・残量・上限・resetのうち何が取得できるかを実測する。金額、回数、tokenなど単位と制限窓、モデル別制限、共有範囲を記録する。
3. 更新直後と再取得を比較して更新遅延を確認する。残量を推定するための大量の生成や、レートリミットまで使い切る試験は行わない。
4. 利用可能なmodel×effortとハーネス固有機能の取得方法を確認する。既存Claude・Codexの観測入口も、現在の契約と実行経路で利用できるか確認する。
5. 取得元ごとに、所有repo・公開入口・取得項目・取得不能項目を確定する。認証は既存の正規入口を利用し、秘密値をrepo・ログ・Jev入力へ渡さない。

**完了条件:** Cursor・Grok両方の実測結果があり、取得できる項目とできない項目を区別できる。継続的に呼べる取得経路が確定している。取得不能なら未解決事項として残し、架空の残量や別契約の数値で次工程の成立を装わない。調査結果は出典・取得日付きでRAGへ保存する。

### 工程2 — 02と推薦契約を確定する

1. 02の各判断を、モデルの能力、必要なeffort、ハーネス由来の機能、運用上の優先順位へ整理する。既存の実測根拠は維持し、推測を性能点数に変えない。
2. 02に推薦用の構造化記述を設け、その記述から候補データと対応する表を生成する。説明文・出典も02から辿れる状態を保ち、公認projectionと同時更新する。
3. ハーネス×モデル×エフォートの候補ID、poolの識別と共有関係、取得状態、入力・出力の型を定める。制限窓が複数ある場合は、各窓の制限を保持する。
4. 必要能力・明示指定を満たす候補に対してCursor優先を適用する。残量率・reset・プラン規模をどう判断材料にするかは工程1の取得項目に合わせる。既存selectorの閾値を根拠なく継承しない。
5. Codex nativeの子と外部CLIの違いを候補の実行可否へ反映する。ハーネス選択を、全ての子をAitermで起動する指示へ読み替えない。

**完了条件:** 同じモデルをCursorと直接ハーネスで使う場合を別候補として表現でき、両者のeffort対応と消費プールを説明できる。親のmodel×effortを変更せずに子の推薦ができる。02と候補データの差異を生成検証で検出できる。

### 工程3 — 残量取得を推薦入口へ接続する

1. 工程1で確定した取得方法を、責務を持つ場所へ実装する。既存quota部品は意味が一致する部分を再利用し、provider名だけで契約を決める箇所を改める。
2. 観測値と実行先をpool IDで関連付け、Cursor内の別モデルによる二重計上を防ぐ。利用可能な窓すべてと、取得不能項目を維持する。
3. 推薦呼出しから収集を実行する。キャッシュの必要性と有効期間は工程1の更新周期・取得コストから決め、観測時刻を必ず返す。古い値を現在の値として扱わない。
4. 通信・認証エラー、未対応、期限切れを最小のfixtureで検証する。取得サービスの内部状態や認証DBを直接書き換える実装を作らない。

**完了条件:** 親の手動準備なしで、一度の推薦呼出しにCursor・Grokの実際の観測が入る。取得失敗が見え、Claude・Codexの既存経路も新しい型で扱える。

### 工程4 — Jevによる3点の推薦を実装する

1. 公式`typesafe-ai` skillの公開APIで、任務・判断基準・適合候補・観測をまとめて渡す。既存の工場配布キーを正規の読込方法で利用する。
2. Jevが選べる対象を実在する候補IDに限定し、modelとeffortを別々に選んで非対応の組合せを作らない。必要な判断項目も同じ呼出しへまとめる。
3. CLIの短いJSON結果を完成させる。詳細な根拠は参照先へ置き、親へ02全文や全候補の長い説明を戻さない。
4. 適合候補なし、Jev API失敗、観測不足を結果へ反映する。選択確率の閾値や独自の多段再試行は、実測による必要性が出た場合だけ導入する。

**完了条件:** 任務の入力から、ハーネス・モデル・エフォート、消費プール、理由、観測時刻まで一回で返る。推薦の受取りだけでは子の起動や親の設定変更は起きない。

### 工程5 — 実務比較・配布・利用開始

次のケースを、取得部品はfixture、推薦は固定ケースと必要なJev実呼出しで確かめる。各機能のfocused test完了後に、所有repoの必須CIと最終通し試験を実行する。

| ケース | 確かめる結果 |
|---|---|
| 同じClaude系・Grok系モデルがCursorと直接入口にある | 必要な機能・effortが使え、枠に余裕があるならCursorを推薦する |
| Cursorの枠が尽きた／別の制限窓に達した | 利用できる適合候補と変更理由を返す。候補がなければ明示する |
| Cursorの複数モデルが同じ枠を使う | モデルを切り替えても枠が増えたと判断しない |
| モデルがcatalogにない／要求effortが非対応 | 存在しない組合せを返さず、明示指定を黙って落とさない |
| 同名effortの意味が異なる／effort指定不可 | 確認済みの対応と意味を使い、指定不可と`none`を区別する |
| 残量不明・古い観測・認証失敗・Jev失敗 | 成功に見せず、原因と推薦可能な範囲を返す |
| 長いcontext・固有の検索／道具・独立した反証が必要 | ハーネスの機能とモデル提供元を評価する。Cursorという同じハーネス名だけで独立性を判定しない |
| オーナーがharness・model・effortを明示した | 指定を尊重し、満たせない場合はその理由を返す |
| 局所修正と難しい設計で必要な計算量が違う | 02の根拠に沿ってeffortを選び、常に最大・常に最小へ固定しない |

同じ代表任務について「親が02を読んで選ぶ場合」と比較し、選択の妥当性、任務の成功率、手戻り、監査工数、親・Jev・実行先を含む総token、所要時間、契約消費を記録する。計測できない項目は欠測と明記し、親のtoken削減だけで全体の効率化を断定しない。初回で削減率を決め打ちせず、悪化した任務は原因を調べて適用範囲を決める。

測定結果は既存の工場の閲覧面へ集計して掲載する。工程2で掲載先と必要な集計項目を確定し、成果物目録との対応を検証する。契約の秘密値、認証情報、任務本文は公開しない。新しい独立ダッシュボードの構築へ範囲を広げない。

各親から呼べる最小の利用案内を配布し、長い02の代わりに推薦入口を案内する。dotagentsのcommit・push、変更が必要だった所有製品の正式release・install、配布後の実呼出しまで行う。既存の固定role設定を復活させたり、契約プランを変更したりする作業は含まない。

**完了条件:** 配布先から実際に呼べて、実残量を使った3点の推薦が返る。比較結果と制限を閲覧でき、親の負担削減と推薦品質を実測で説明できる。使われない収集部品や未接続の試作品を完成としない。
