# 工場エラーの発生版・再発判定・最新報告の修理

## 目的と承認

2026-09-13のオーナー依頼に基づき、BugHubで最新の製品版に関する障害を優先して確認できるようにする。解決済みの過去の記録は対応対象へ戻さず、同じ版で実際に再発したエラーは表示する。修理、検証、公開、対象端末への導入、WebUIでの確認までを本campaignに含める。

## 責務と工程

- 製品が保存している実際の発生版を公開runtime契約へ通す。発生版がない既存記録には報告時の版を代入しない。
- dotagentsは公開データの投影と定期報告の正規入口を修理する。
- ServerManagerはBugHubの再発判定、発生版の表示、正式な履歴再評価を所有する。
- 過去に失敗した診断は、現行版で対象機能を確認する。未実施や適用外を成功へ読み替えない。
- consumerから先に互換性を整え、製品の正規releaseとinstallerで届ける。稼働設定やissueを手作業の上書きで修理しない。

## 成功条件

1. 件数・最終発生時刻が同じruntime記録を再送しても、インストール版の更新だけでは再発しない。
2. 解消後の新しい発生を、同版を含めて検出する。遅延reportで新しい状態を巻き戻さない。
3. WebUIで発生版と現行の導入版を区別でき、最新発生、古い未解決、解決済みを判別できる。解決済みは既定の対応一覧に出ない。
4. 既存の誤判定は保存済みの一次観測から正式入口で再評価し、修復の根拠を残す。
5. 定期報告が正規入口から届き、鮮度表示と運用周期が整合する。製品更新の合意済み周期は維持する。
6. 調査で見つかった工場エラーを現行版で再確認し、解消または未解明の根拠を公開面から確認できる。

## 既知の罠と検証

累積snapshotの再送は新規発生ではない。snapshot上位のversionは実行した製品版であり、recordの発生版とは異なる。ackは配送確認であり解消ではない。診断のskipped/not_applicableは対象機能の成功を証明しない。履歴の削除や、日数だけでの自動解消は行わない。

変更箇所の既存focused testをbaselineとし、再送・同版再発・遅延報告・版不明・明示解消の最小再現を先行させる。定期実行は最小PATHと生成スケジュールの試験で確認する。各repoの関連gate、最後にrelease必須gateを実施し、公開後は版、正規診断、report受信、WebUIを確認する。

## 統括と並列化の裁定

複数repoの書込み調整と受入の連鎖があるため統括レーンとする。公開契約・履歴修復・公開操作は親が裁定する。read-onlyの製品投影調査を委譲し、親は受入契約とBugHub実装を進める。同一repoのwriterは一人に限定する。Lattice工程管理の新規適用はしない。生きた作業場の未commit変更を保護するため専用worktreeを使う。

## 現在地

BugHubの再送判定・発生版表示・履歴再評価と、dotagentsの版投影・定期報告を実装した。Aiterm/sidecarは旧集約の復元不能な発生版を不明として移行する。製品の公開投影と移行はfocused testで確認済み。現在は関連gateと製品ごとの公開前検査を進めている。公開・本番の変更は未実施。

Chat Proの相談には対象commit、実コード、テストの実測、具体的な問いを渡す。要約だけの回答は実装判断の根拠にしない。公式uploadが確定するMIMEの不一致を受け入れず添付を拒否する欠陥と、Proを3分で打ち切る欠陥を修理した。実コード添付のMCP相談でPro・読戻し・回答完了を実測した。並行して公開された会話継続機能を統合済み。
